This orphan branch contains only the deterministic container wrapper for the immutable Destiny release `step-zero-v1.1`. The verified source is checked out separately during the workflow, and the former `staging/destiny/` prefix was a Replit workspace artifact rather than a repository path.

The staging candidate is preserved at wrapper commit `40957e73bf7ecca97db95f6a101708d8c845aa61`. The current wrapper builds a distinct production-configured candidate from the same source SHA and tag because Next.js inlines the Supabase and site identity at build time. The final hostname is `https://app.caminoseo.com` and is pinned literally in the workflow, Dockerfile, and this runbook. This wrapper must never be merged into `main` without a separate CTO decision.

Production runs are push-triggered only by `production/run.json` on the orphan `container-staging` branch. The shared budget is three runs across candidate and post-cutover combined: run 1 is the candidate, run 2 is post-cutover, and run 3 is reserved for a CTO-approved candidate retry. The audited wrapper commit intentionally omits `production/run.json`; adding the candidate manifest is the separate run-1 commit after every pre-run gate passes.

The candidate starts only when `destiny-production` is empty. If a failed candidate left a machine behind, that assertion fails and the failure-only cleanup destroys the leftover machine and proves the app is empty. A third-run retry can therefore self-heal the disposable target, but only after a separate CTO decision authorizes that retry.

Before run 1, the `destiny-production` Fly certificate for `app.caminoseo.com` must be issued, the production Supabase Auth redirect allowlist must include `https://app.caminoseo.com/**`, the production GitHub environment must contain the seven required secrets plus `NEXT_PUBLIC_SUPABASE_URL`, and the release evidence must record the staging-secret/env diff and the host-redirect scan. The Supabase Auth Site URL remains `https://destiny-seo.replit.app` throughout this parallel release; changing it is a separate traffic-migration decision. The candidate phase builds and deploys one immutable digest to the empty Fly app, rejects every staging identity from the image, proves the compiled production Supabase and hostname identities, sweeps 79 routes (the 76-route inventory plus three public build stamps), and observes a 30-minute pre-cutover window. A failed candidate captures logs and machine state, then destroys every candidate machine and proves the app is empty.

After candidate success and before DNS, run the authenticated ClearCheck smoke against the final hostname using a local hosts-file override: sign in against production Supabase, load the dashboard, submit one keyword verdict, and confirm `/api/content/word` returns 200. Only then cut over DNS and commit `production/run.json` with `phase: post-cutover` and the recorded candidate digest. The post-cutover phase verifies that exact platform manifest, repeats the route sweep, and observes the second 30-minute window.

`https://app.caminoseo.com` is a new hostname and does not currently serve the Replit deployment, so this release is a parallel launch rather than a migration of existing traffic. If a rollback trigger fires after DNS is added, remove the new hostname's DNS records. The existing `https://destiny-seo.replit.app` deployment remains production of record and is not decommissioned, redirected, or modified by this release. Moving real users or the existing Replit origin to Fly requires a separate CTO decision.
